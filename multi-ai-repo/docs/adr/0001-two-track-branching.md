# ADR 0001：双轨分支模型

- 状态：已接受
- 日期：2026-11-02

## 背景

仓库同时有多个 AI 代理和人类开发者。两类代码的生命周期完全不同：

- **设计中的原型**：频繁推翻，可能整体丢弃，不需要长期维护。
- **正式开发的代码**：已经对用户负责，需要测试、评审、版本化和可回滚。

如果两者共用一条主干，会出现三种问题：原型半成品被正式代码引用；正式开发的评审成本
拖慢原型试错；原型被推翻后难以从主干中干净移除。

## 决策

1. **目录隔离**：原型放 `prototypes/<slug>/`，正式代码放 `apps/` `packages/` `services/`。
2. **分支隔离**：每个原型有独立的集成分支 `proto/<slug>`；`main` 只承载正式代码。
3. **契约先行**：每个任务先有 `ai/tasks/<ID>.yml`，声明路径白名单与验收标准，PR 上机器校验。
4. **单一合流**：所有合并走 squash；`main` 开启 merge queue，保证线性历史。
5. **一次性转正**：原型通过 `promote/<slug>` PR 用 `git mv` 搬进正式目录，
   同时写 ADR 并保留 `prototype.yaml` 作为决策记录。

## 后果

好处：

- 原型可以快速迭代、整体丢弃，不影响 `main`。
- 多个 AI 的写入范围由契约限定，冲突从文件级降到任务级。
- 每个任务对应一个 commit，回滚粒度清晰。
- 原型转正有明确的人为决策点和审计记录。

代价：

- 多一层分支（`proto/<slug>`），需要维护原型的生命周期。
- 转正时有一次性搬移成本，且搬移后不能自动同步原型的后续改动。
- 需要配置分支保护、required checks、merge queue，初始设置成本高于「直接推 main」。

## 被否决的方案

- **所有 AI 直接推 main**：无法隔离原型，回滚粒度差，冲突不可控。
- **每个 AI 一个 fork**：跨 fork 的权限和分支保护配置更复杂，内部协作收益不足。
- **用 claims 文件做文件锁**：Git 没有原子锁，AI 崩溃后锁不释放，反而引入新的冲突面。
- **原型和正式代码同目录、靠命名区分**：边界靠自觉，无法用 CI 强制。
